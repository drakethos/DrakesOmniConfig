# Plan: OmniConfig vs WackyDB, same job, timed

Goal: show DrakesOmniConfig makes the same kind of content as Wacky's Database (WackyDB) **faster and lighter**:
game start, world load, memory, and in-game frame time, for a small and a near-all-items loadout. Only what both
mods can do is compared.

## What is compared (capability-matched)

Both mods get the identical content, generated from one list:

| Capability | WackyDB | OmniConfig |
|---|---|---|
| New item cloned from a vanilla item, own id and name | Items/*.yml `clone` | `clones:` |
| Stat changes on it (weight, value, damage, durability, food) | item yml fields | clone `fields:` |
| Crafting recipe (station, level, amount, ingredients) | Recipes/*.yml | clone `recipe:` |
| Recolour (material colour) | Materials / item colour | `looks/*.json` tint |
| Server → client sync | ServerSync | ServerSync |

Left out on purpose: WackyDB's creatures, pickables, effects/AoEs, status-effect creation, piece cloning into build
menus; OmniConfig's node rules, admin panel, live `looks.put`. If WackyDB's recolour works differently (material
swap rather than tint), we compare its closest equivalent and say so in the report.

## Loadouts

Generated by one script (`Tools/bench/make_loadout.py`, to write) from `GameDataManifest.json`, into both formats:

- **Small:** 10 items (weapons, armour, food): clone + 3 stat changes + recipe + recolour each.
- **Massive:** every vanilla item that can be cloned (~500): clone + 3 stat changes + recipe + recolour each.
- **Baseline:** neither mod, same profile otherwise, to subtract the game's own cost.

## Measurements

From DrakesTestLab's run report (`latest.json`) and BepInEx log timestamps:

1. **Game start:** process start to main menu; plus each mod's own `Awake` time (TestLab `modLoad`).
2. **World load:** `ZNet.LoadWorld` to the player in the world (TestLab `worldReadySeconds`), and the mod's own
   registration time (first to last log line of its item build).
3. **Memory:** managed heap and total after world load (TestLab `memoryNowMb`).
4. **Frame time in play:** 60 s standing in the test world plus opening the inventory and a crafting station
   with the new items (TestLab frame stats: average, 1 % low, hitches).
5. **Sync (second stage, needs two instances):** payload size and time from join to items usable on the client.

## Method

- Two Gale profiles cloned from `drakeTest`'s base (BepInEx, Jotunn, DrakesTestLab only): `benchOmni`, `benchWacky`.
  Same game build, same world, same character.
- Each run goes through the Valheim queue. Per mod and loadout: 1 warm-up run (discarded), then 5 cold runs; report
  median and spread. Order alternates Omni/Wacky to even out disk cache and thermals.
- The TestLab suite `Bench-Content` (to write) only waits, opens the inventory and a station, and records; it
  checks every loadout item exists in both mods first, so a run that silently built fewer items cannot "win".
- Each mod at its default settings. If WackyDB's cache file changes start-up time, it is measured both cold
  (cache deleted) and warm, and reported separately.

## Deliverable

A short report (table per loadout: start, world load, own registration time, memory, FPS, plus a chart) and the raw
`latest.json` files. If OmniConfig loses anywhere, the report says where, and the profile data goes to a fix.

## Needs before starting

- WackyDB itself: not on this machine (only an empty config folder in `Profiles/conflictPack`). It has to be
  downloaded from Thunderstore (WackyMole-WackysDatabase), which needs the owner's OK and a pinned version.
- The looks bridge passing its in-game tests (NR-40..NR-42) first, so the recolour half is measurable.
